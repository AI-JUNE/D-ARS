# D-ARS 백업·복구 런북 (RUNBOOK)

작성 2026-09-03 (126회차). 대상: 운영 담당자. 목적: **데이터가 사라지거나 망가졌을 때 무엇을, 어떤 순서로 하는가**를 한 장에 고정한다.

원칙
- 이 문서의 절차 중 **파괴적·비가역 단계(복구 대상 덮어쓰기, 브랜치 삭제, 운영 전환)는 사람이 수행한다**. 자동화는 하지 않는다. **[승인 필요]**
- 복구는 "명령을 쳤다"가 아니라 **확인 대상 표 전부의 존재·행수·화면 동작을 확인**해야 끝난다. 확인 목록은 코드(`lib/backupCheck.js`의 `COVERED_TABLES`)에 단일 출처로 두고, 테스트가 스키마와 대조한다 → 새 표가 추가되면 이 문서를 갱신하지 않는 한 테스트가 실패한다.

## 1. 무엇을 지키는가 (데이터 자산)

| 대상 | 위치 | 유실 시 영향 | PII |
|---|---|---|---|
| `scenarios` | Neon Postgres | 시나리오 정의·버전 소실 → 서비스 정지급 | 없음 |
| `docs` | Neon Postgres | 서류 마스터 소실 → 발송 기능 정지 | 없음 |
| `visual_sessions` | Neon Postgres | 상담 이력·통계 소실 | **있음(phone)** |
| `ums_log` | Neon Postgres | 발송 이력 소실 → 분쟁 대응 불가 | **있음(phone)** |
| `daily_stats` | Neon Postgres | 일별 집계 소실(원천에서 재계산 가능성 있음) | 없음 |
| `audit_events` | Neon Postgres (`AUDIT_DB=1`일 때만) | 접근·감사 이력 소실 → 규제 대응 근거 상실 | 마스킹된 값만 |
| 애플리케이션 코드 | Git 원격 + Vercel 배포 이력 | 재배포로 복구 가능(별도 백업 불필요) | 없음 |
| 환경변수·시크릿 | Vercel 프로젝트 설정 | 재주입 필요. **DB 백업에 포함되지 않는다** | 해당 |

> 시크릿은 백업 대상이 아니라 **별도 보관 대상**이다. 보관처·보관 방식 결정은 사람이 한다. **[승인 필요]**

## 2. 백업 수단 (현행)

- **DB**: Neon 의 시점 복구(PITR)·브랜치 기능에 의존한다. 보존 기간과 사용 가능한 시점 범위는 **요금제에 따라 다르므로 Neon 콘솔에서 직접 확인**한다(이 문서에 숫자를 적어 두면 요금제 변경 시 조용히 거짓이 된다).
- **논리 백업(선택)**: 시점 복구와 별개로 파일 사본이 필요하면 `pg_dump` 로 받는다. 저장 위치·주기·암호화 결정은 사람이 한다. **[승인 필요]**
  ```
  pg_dump "$DATABASE_URL" --no-owner --no-privileges -Fc -f dars-YYYYMMDD.dump
  ```
- **스키마**: `db/schema.sql`·`db/audit.sql` 은 멱등(`create table if not exists`)이라 빈 DB 에 재적용할 수 있다. `npm run db:setup` 은 `schema.sql` + **`seed.sql`(데모 데이터)** 를 함께 적용하므로 **운영 복구에는 쓰지 않는다.**
- 현재 라이브(d-ars.vercel.app)는 데모 구성이며 운영 DB 백업 정책은 미확정이다(`docs/STAGING_OPERATIONS.md` 5장과 일치).

## 3. 목표값 (RPO/RTO)

**미확정.** 허용 데이터 손실 시간(RPO)과 복구 목표 시간(RTO)은 계약·요금제에 따라 정해지는 값이라 임의로 적지 않는다. 확정 절차: (1) 고객사 요구 수준 확인 → (2) Neon 요금제의 실제 복구 가능 범위 확인 → (3) 여기에 기입하고 계약서와 대조. 확정 전에는 "베스트 에포트"로만 안내한다.

## 4. 복구 절차

사고 유형을 먼저 가른다. **오판하면 멀쩡한 데이터를 덮어쓴다.**

| 유형 | 증상 | 절차 |
|---|---|---|
| A. 앱 장애 (데이터 정상) | `/api/health` 503 인데 DB 는 살아 있음 | 복구 아님 → Vercel Instant Rollback (6장) |
| B. 데이터 오염·오삭제 | 특정 표의 행이 사라짐/변조됨 | 아래 B 절차 |
| C. DB 전체 소실 | 접속 자체 불가·인스턴스 없음 | 아래 C 절차 |

### B. 데이터 오염·오삭제

1. **멈춘다.** 추가 쓰기를 막는다(해당 기능 비활성 또는 유지보수 공지). 오염된 상태로 계속 쓰면 복구 시점이 계속 나빠진다.
2. **시점을 정한다.** 사고 직전 시각을 로그(`lib/log.js` 구조화 로그의 `ts`)·감사 이벤트(`audit_events`)로 특정한다.
3. **운영에 바로 복구하지 않는다.** Neon 콘솔에서 그 시점의 **새 브랜치**를 만든다(운영 브랜치는 그대로 둔다).
4. 새 브랜치 접속 문자열로 **확인 대상 표**(1장 표 + `COVERED_TABLES`)의 존재·행수를 확인한다.
5. 필요한 데이터만 운영으로 되돌린다. 표 전체 교체가 필요하면 사람이 SQL 을 검토한 뒤 실행한다. **[승인 필요 — 비가역]**
6. 복구 후 5장 6단계(`app`)와 동일하게 화면·`/api/health` 를 확인하고, 사고·조치 내역을 기록한다.

### C. DB 전체 소실

1. 새 Neon 프로젝트/브랜치를 만든다(가능하면 마지막 정상 시점에서 복구).
2. 백업이 시점 복구가 아니라 덤프뿐이면: 빈 DB 에 `psql "$NEW_URL" -f db/schema.sql` → `psql "$NEW_URL" -f db/audit.sql` → `pg_restore --no-owner -d "$NEW_URL" dars-YYYYMMDD.dump`. **`db/seed.sql` 은 적용하지 않는다**(데모 데이터가 운영에 섞인다).
3. 확인 대상 표 전부의 존재·행수를 확인한다.
4. Vercel 의 `DATABASE_URL` 을 새 값으로 교체한다. **사람이 대시보드에서 직접 한다. [승인 필요]**
5. 재배포 후 `/api/health` 가 200·`db=connected` 인지 확인한다.

### 확인 대상 표 (복구 완료 판정 기준)

`scenarios` · `docs` · `visual_sessions` · `ums_log` · `daily_stats` · `audit_events`

이 목록은 `lib/backupCheck.js`의 `COVERED_TABLES` 와 동일해야 하며, `tests/backupcheck.test.mjs` 가 `db/*.sql` 선언과 양방향으로 대조한다(표가 늘거나 줄면 테스트가 실패해 이 문서 갱신을 강제한다).

## 5. 복구 리허설 (정기 점검)

리허설은 **운영이 아닌 대상**에 대고 한다. 운영 DB 를 상대로 하는 리허설은 리허설이 아니라 사고다.

필수 단계 — 하나라도 빠지면 "리허설했다"의 근거가 되지 않는다(`REHEARSAL_STEPS`).

| 단계 | 코드 | 내용 |
|---|---|---|
| 1 | `snapshot` | 복구 시점(스냅샷·브랜치)을 선택하고 그 근거를 기록 |
| 2 | `restore` | 별도 대상(운영 아님)으로 복구를 **실제로** 수행 |
| 3 | `schema` | 확인 대상 표 전부의 존재·주요 컬럼 확인 |
| 4 | `rowcount` | 표별 행수를 원본과 대조 (`compareRowCounts` — 감소는 무조건 실패) |
| 5 | `app` | 앱이 복구본을 보게 하고 `/api/health` 200 · 주요 화면(세션·시나리오·서류) 확인 |
| 6 | `signoff` | 사람이 결과를 확인하고 이름을 남김 |

주기 기준: 기록이 **90일**(`DEFAULT_REHEARSAL_MAX_AGE_DAYS`)을 넘으면 근거로 보지 않는다. 분기 1회 점검 관례에 맞춘 **운영 기준값이며 실측 지표가 아니다** — 계약 요건에 맞춰 조정한다.

### 기록 방법

`docs/restore-rehearsal.json` 에 한 건씩 추가한다(삭제하지 않고 누적).

```json
{ "at": "2026-09-03T10:00:00+09:00", "by": "담당자명",
  "steps": ["snapshot", "restore", "schema", "rowcount", "app", "signoff"],
  "note": "복구 시점·대상·행수 대조 결과 요약" }
```

판정: `rehearsalStatus(records)` → `none`(미실시) / `incomplete`(단계 누락) / `stale`(90일 초과) / `ok`.

### 리허설 이력

| 일시 | 수행자 | 결과 |
|---|---|---|
| — | — | **미실시** |

현재 상태: **`none`(미실시)**. 리허설은 실제 Neon 프로젝트에 복구를 수행해야 하므로 자동화가 대신할 수 없다 — 사람이 수행하고 위 파일에 기록한다. **[승인 필요]**

## 6. 롤백 (앱 장애 · 데이터 무관)

1. Vercel → 해당 프로젝트 → Deployments → 직전 정상 배포 → **Instant Rollback**.
2. `/api/health` 200 · `commit` 값이 되돌린 배포의 SHA 인지 확인.
3. 코드 되돌리기가 필요하면 새 커밋으로 되돌린다. **`git reset`·`git revert` 로 이력을 고치지 않는다.**

## 7. 금지선 (자동화가 하지 않는 것)

- 운영 DB 에 대한 복구·덮어쓰기·`drop`/`truncate` 실행 — 전부 사람이 한다.
- 백업 파일의 외부 전송·업로드(개인정보 포함 가능).
- Neon·Vercel 설정 변경(브랜치 삭제, `DATABASE_URL` 교체, 요금제 변경).
- 리허설 기록의 **수정·삭제** — 추가만 한다.
