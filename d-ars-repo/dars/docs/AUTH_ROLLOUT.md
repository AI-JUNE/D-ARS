# D-ARS 실인증 전환 준비 (AUTH_ENFORCE) — 운영 계정·역할 매핑

작성 2026-09-07. 목적: `AUTH_ENFORCE=1` 로 **실제 접근 차단을 켜기 전에** 무엇이 갖춰져야 하는지,
운영 계정과 역할을 어떻게 발급·매핑하는지 정한다.

> **활성화는 사람의 승인 사항이다.** 자동화는 코드·문서·점검까지만 하고, 실계정·실키 주입과
> `AUTH_ENFORCE=1` 설정은 사람이 Vercel 대시보드에서 직접 한다. **[승인 필요]**

## 1. 지금 상태와 위험

- 라이브(d-ars.vercel.app)는 **비강제(데모) 모드**다. `lib/auth.isEnforced()` 가 false 라 `guardWrite` 는 통과만 시킨다.
- 이 상태에서 스위치만 켜면:
  - `AUTH_USERS` 미설정 → 저장소에 공개된 **데모 계정 3종이 그대로 운영 계정**이 된다.
  - `AUTH_SECRET` 미설정 → 코드에 박힌 데모 고정값으로 세션을 서명한다. 같은 값을 아는 사람은 **토큰을 위조**할 수 있다.
- 그래서 "켰다"와 "실인증이 된다"는 다른 상태다. 아래 2·3장을 채운 뒤에만 켠다.

## 2. 역할 정의

| 역할 | 대상 | 할 수 있는 일 |
|---|---|---|
| `viewer` | 고객사 열람 담당 | 대시보드·통계 열람 |
| `operator` | 상담 운영자 | 시나리오·서류·UMS 등 운영 데이터 편집 |
| `admin` | 고원 운영 관리자 | 위 전부 + 감사 로그·런처 등 관리 기능 |

등급은 `viewer < operator < admin` 누적이다(`lib/auth.roleAtLeast`). 역할은 이 3종뿐이며,
목록에 없는 값을 넣으면 **모든 권한 판정에서 탈락**한다(점검 CLI 가 blocker 로 잡는다).

## 3. 경로별 최소 역할 (코드와 동기화됨)

아래 표는 `lib/auth.js` 의 `routeRoleMatrix()` 와 **양방향으로 대조**된다
(`tests/authreadiness.test.mjs`) — 코드에 경로가 추가·변경되면 이 표를 고치기 전까지 테스트가 실패한다.
표에 없는 경로의 최소 역할은 `viewer`(로그인만 하면 열람)다.

| 경로 | 최소 역할 | 비고 |
|---|---|---|
| `/admin` | admin | 감사 로그 등 관리 화면 |
| `/api/admin` | admin | 관리 API — 라우트 `guardWrite` 와 이중 게이트 |
| `/launcher` | admin | 데모·시연 런처 |
| `/ums` | operator | 발송 이력·발송 기능 |
| `/scenarios` | operator | 시나리오 편집 |
| `/docs` | operator | 서류 마스터 편집 |
| `/templates` | operator | 템플릿 편집 |

## 4. 계정 발급 절차 (사람이 수행)

1. 역할별로 **최소 인원**만 발급한다. `admin` 은 실제로 감사 로그를 봐야 하는 사람만.
2. `AUTH_SECRET` 을 새로 만든다 — 32자 이상 무작위 값(예: `openssl rand -base64 48`). 데모값·다른 환경 값 재사용 금지.
3. `AUTH_USERS` 를 JSON 배열로 만든다. 형식:
   ```json
   [{ "u": "아이디", "p": "비밀번호", "role": "admin", "name": "표시이름" }]
   ```
   비밀번호는 12자 이상, 데모 비밀번호 재사용 금지, 계정마다 다른 값.
4. Vercel 환경변수에 주입한다(스테이징 → 운영 순서, 값은 환경별로 다르게). 환경 매트릭스는 `docs/STAGING_OPERATIONS.md` 2장.
5. `npm run auth:check` 로 **차단 사유 0건**을 확인한다(값은 출력되지 않는다 — 설정 여부·길이·마스킹된 계정만).
6. 마지막에 `AUTH_ENFORCE=1` 을 켜고, 로그인·역할 게이트·401/403 을 스테이징에서 확인한 뒤 운영에 승격한다.

## 5. 점검 CLI

```
npm run auth:check
```

- 현재 프로세스의 환경변수를 **읽기만** 한다. 아무 것도 켜지 않고, 비밀값을 출력하지 않는다.
- blocker 가 있으면 종료코드 1, warning 만 있으면 0(전환은 가능하되 위험이 남았다는 뜻).
- 판정 로직은 `lib/authReadiness.js`(순수 함수), 근거 테스트는 `tests/authreadiness.test.mjs`.

## 6. 한계 (정직하게)

- `AUTH_USERS` 는 **평문 비밀번호를 환경변수에** 둔다. 해시 저장·계정 DB·SSO 는 아직 없다.
  소수 운영 계정 규모에서만 감당되는 방식이며, 고객사 단위 계정이 늘어나면 계정 저장소가 필요하다 **[승인 필요]**.
- 비밀번호 회전 주기·잠금 정책은 계약·운영 정책에 종속이라 임의 수치를 적지 않았다.
- 이 문서와 CLI 는 **설정의 형태**만 검증한다. 실제 로그인 성공 여부는 스테이징에서 사람이 확인한다.
