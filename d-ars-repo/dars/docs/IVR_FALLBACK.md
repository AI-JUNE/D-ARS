# 장애 폴백 — 엔진 오류 시 기존 음성 IVR 전환 계약

정본 로직: `lib/ivrFallback.js` (테스트 `tests/ivrfallback.test.mjs` 가 이 문서와 코드·문구·기준값을 대조한다).

## 원칙
보이는 ARS 는 통화에 화면을 **덧붙이는** 제품이다. 화면 쪽(D-ARS 엔진)이 어떤 이유로든 실패해도
통화는 끊기지 않아야 하고, 콜봇은 **화면 없이 기존 음성 IVR 로 즉시 계속**한다.
그래서 "응답이 없거나 이상하면 음성" 이 기본이고, 화면 진행은 D-ARS 가 **명시적으로 `visual`** 이라고
말한 정상 응답에서만 한다.

## 응답 계약 (콜봇 대면 라우트 전부)
`POST /api/cpaas/voice`, `POST /api/visual/action` 의 응답 본문에는 `fallback` 이 **항상** 실린다.

```json
{ "ok": true, "...": "...", "fallback": { "mode": "visual" | "ivr", "reason": "<코드>|null", "message": "<콜봇이 읽을 문구>" } }
```

| mode | 뜻 |
|---|---|
| `visual` | 화면 경로 정상 — 콜봇은 "화면으로도 함께 안내해 드립니다." 를 말하고 화면 동반 진행 |
| `ivr` | 화면 경로 불가 — 콜봇은 `message` 를 읽고 기존 음성 IVR 시나리오로 계속 |

`ivr` 일 때 `message` 는 고정: **화면 안내를 이용할 수 없어 음성 안내로 계속 진행합니다.**

### reason 코드
| 코드 | 어디서 | 상황 | HTTP |
|---|---|---|---|
| `SMS_FAILED` | `/api/cpaas/voice` | 세션은 만들었으나 화면 링크 문자 발송 실패(게이트웨이 오류·`SMS_GATEWAY_URL` 미설정) | 200 |
| `RELAY_FAILED` | `/api/visual/action` | 고객이 화면에서 누른 선택을 콜봇 콜백(`CALLBOT_CALLBACK_URL`)에 3회 재시도 끝에 전달 실패 | 200 |
| `ENGINE_ERROR` | `/api/cpaas/voice` | 처리 중 예외(DB 드라이버 오류 등). 오류 원문은 서버 로그에만 남고 응답에는 실리지 않는다 | 503 |
| `SCREEN_LOST` | 고객 화면 `/visual` | 서버 상태 조회가 연속 실패 — 화면이 스스로 음성 전환을 안내 | — |

멱등 재호출(같은 callId 로 콜봇이 재시도)은 이미 링크가 나간 상태이므로 `visual` 이다.

### 봉투 옆자리 — 아웃바운드 결과(`sms` · `relayed`)
두 라우트는 `fallback` 봉투와 **나란히** 아웃바운드 호출 결과를 싣는다(`sms` · `relayed`).
그 객체도 봉투와 같은 규칙을 지킨다 — **고정 어휘만** 담고 오류 원문·주소·전화번호를 담지 않는다
(`lib/cpaas.CPAAS_FAIL_REASONS` 단일 출처 · 원문은 서버 로그에만 남는다).

| 필드 | 값 |
|---|---|
| `ok` | 전달 성공 여부(불리언). 판정이 보는 유일한 필드 |
| `provider` | `mock` \| `http` |
| `mocked` | mock 프로바이더에서만 `true` |
| `status` | 응답이 도착했을 때의 HTTP 상태 |
| `reason` | 실패 사유 — `not_configured` \| `timeout` \| `network` \| `http` |
| `attempts` · `failed` | 릴레이 재시도 횟수와 소진 여부(`relayed` 전용) |

한동안 이 자리는 `error: <오류 원문>` 을 들고 있었고, `fetch` 실패 메시지에는 대상 주소가 붙으므로
`SMS_GATEWAY_URL`·`CALLBOT_CALLBACK_URL` 이 응답으로 새어 나갔다(`/api/visual/action` 을 받는 쪽은
**고객 브라우저**다). mock 에서는 `to`·`text`, 즉 **가리지 않은 발신번호와 서명 링크**까지 실렸다 —
같은 라우트가 DB 에는 `maskPhone` 을 쓰면서 응답에는 원문을 실은 셈이다.

## 콜봇 측 판정 (참조 구현 `callbotShouldUseIvr`)
다음 중 하나면 음성 IVR 로 계속한다.
1. HTTP 상태가 2xx 가 아니다 — 401/429/503 포함. 네트워크 오류·타임아웃도 여기에 해당
2. 본문이 JSON 이 아니거나 `ok !== true`
3. `fallback` 필드가 없다(계약 위반 — 구버전 엔진·프록시 오류 등, 보수적으로 음성)
4. `fallback.mode !== 'visual'`

권장 타임아웃: 콜봇 → D-ARS 웹훅 호출은 통화 흐름을 막지 않도록 **짧게(수 초)** 잡고, 초과 시 위 1번으로 처리한다.
콜봇은 D-ARS 응답을 **기다리지 못하더라도** 첫 음성 안내를 시작할 수 있어야 한다(화면은 부가 채널).

## 고객 화면 쪽 (`/visual?s=<token>`)
- 상태 조회(`/api/visual/state`) 폴링(2.5초)이 **연속 4회** 실패하면(≈10초) 화면 상단에
  **화면 연결이 끊겼습니다. 전화 음성 안내로 계속 진행해 주세요.** 를 `aria-live="assertive"` 로 표시한다.
- 성공 1회로 즉시 사라진다(일시 지터 1~2회에는 반응하지 않음).
- 만료 토큰(410)도 같은 경로로 안내된다 — 어차피 화면으로는 진행할 수 없기 때문.
- **폴링 요청 하나에는 2초 상한이 걸린다**(주기 2.5초보다 짧다). 이 상한이 없으면 서버가
  응답하지 않는 상태에서 `fetch` 가 성공도 실패도 하지 않아 위 연속 실패 카운터가 **한 번도
  올라가지 않고** 끊김 안내가 영영 뜨지 않는다 — 응답 없음이 무장애로 취급되는 것이다.
  주기·상한·실패 기준은 `lib/ivrFallback` 상수 단일 출처이며 `tests/nohang.test.mjs` 가
  "상한 < 주기" 와 "응답 없는 서버에서 안내가 실제로 켜진다" 를 함께 고정한다.

## 우리가 바깥으로 거는 요청 (`lib/cpaas`)
- 판정(`decideInbound`·`decideRelay`)이 읽는 값은 **우리가 제3자에게 건 요청의 결과**다. 그래서
  그 요청에도 **2초 상한**이 걸린다(`RELAY_TIMEOUT_MS`). 상한이 없으면 게이트웨이가 연결만 살려
  두고 응답하지 않는 상태에서 `sendSms`·`notifyCallbot` 이 성공도 실패도 돌려주지 않고, 그러면
  판정이 **한 번도 불리지 않아** `fallback` 봉투를 실은 응답이 아예 나가지 않는다 — 위 1번
  (콜봇 타임아웃)이 유일한 방어선으로 밀려난다. 고객 화면 폴링 상한과 **같은 이유**다.
- 릴레이 재시도는 `RELAY_MAX_ATTEMPTS` 회 · 백오프 기준 `RELAY_RETRY_BASE_MS`. 최악 소요는
  **요청 시간과 백오프를 함께** 세어 `relayWorstCaseMs()` 가 돌려주고(3×2초 + 0.6초 = 6.6초),
  그것이 서버리스 예산 `RELAY_BUDGET_MS`(10초) 안에 든다는 것을 `tests/nohang.test.mjs` 가
  고정한다. 넘으면 플랫폼이 함수를 먼저 끊고, 그때 콜봇이 받는 것은 봉투가 아니라 아무것도 아니다.
  (이 문서는 한동안 그 셈을 **백오프만** 세어 「≈0.6초 후」라고 적었다 — 아래 2번이 그 자리다.)

## 운영 확인 절차
1. `CPAAS_PROVIDER=http` + `SMS_GATEWAY_URL` 을 일부러 비운 스테이징에서 `/api/cpaas/voice` 호출 → 200 · `fallback.mode=ivr` · `reason=SMS_FAILED` · `sms.reason=not_configured`
2. `CALLBOT_CALLBACK_URL` 을 **응답 없는 주소**로 두고 `/api/visual/action` 호출 → 200 · `reason=RELAY_FAILED` · `relayed.reason=timeout`. 걸리는 시간은 최악 **≈6.6초**(요청 상한 2초 × 3회 + 백오프 0.6초)이고, 주소가 **연결을 거부**하면 즉시 떨어져 ≈0.6초다 — 두 경우를 구별해 확인한다
3. 콜봇 벤더 시나리오에서 위 두 응답과 **연결 거부(타임아웃)** 세 경우 모두 음성 IVR 로 이어지는지 통화로 확인

## 한계 (정직하게)
- 이 계약은 D-ARS 쪽 절반이다. **콜봇/CPaaS 시나리오가 실제로 `fallback` 을 읽고 분기하는지는 벤더 연동 시 통화 리허설로 확인해야 한다** — 리허설 실시는 [승인 필요](실회선·실발신).
- `ENGINE_ERROR` 는 라우트 핸들러 안에서 잡힌 예외에만 해당한다. 플랫폼 수준 장애(함수 콜드스타트 실패·리전 장애)는 응답 자체가 없으므로 콜봇 타임아웃 규칙(1번)이 유일한 방어선이다.
- 화면 연속 실패 기준 4회·상한 2초는 운영 기준값이지 실측 지표가 아니다.
- 이 문서는 한동안 위 상한 없이 "연속 4회 실패하면 안내한다" 고만 적고 있었다. 실패를 **세는**
  규칙은 있었지만 응답 없는 요청이 실패로 **세어지지 않는다**는 사실이 빠져 있었던 것이다.
  (같은 사실이 **우리가 바깥으로 거는 요청**에도 한동안 빠져 있었다 — 그쪽은 문장만 빠진 것이
  아니라 **상한 자체가 없었다**. 「응답 없는 요청은 반드시 끝난다」 가드가 보는 범위가
  화면(`app/**/*.jsx`)뿐이어서, 멈출 가능성이 가장 큰 자리가 아무 대조도 받지 않았다.)
- 아웃바운드 상한 2초·재시도 3회·예산 10초는 운영 기준값이지 실측 지표가 아니다. 예산 10초는
  Vercel 함수 기본값을 가리킨다 — `vercel.json` 에 `maxDuration` 을 적어 바꾸는 날 이 값도
  함께 바꿔야 하고, 그때 어긋나면 위 최악 소요 대조가 먼저 깨진다.
- 상한이 실제로 걸리는지는 **단위 테스트(멈추는 가짜 게이트웨이)** 로만 확인했다. 실제 게이트웨이가
  헤더만 보내고 본문을 흘리지 않는 상황은 재현하지 않았다 — 지금 이 경로는 본문을 읽지 않으므로
  (`r.ok`·`r.status` 만 본다) 그 상태에서도 멈추지 않지만, 본문을 읽게 되는 날 다시 봐야 한다.
